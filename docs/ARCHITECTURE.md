# 实现与兼容性

## 为什么不是复制目录就够了

此客户端存在界面单实例检查、全局命名互斥对象和后台 RPC 服务的重复界面检查。界面、提权服务、连接后台及虚拟网卡都需要分别处理。

脚本只修改本机原版 EXE 的副本，通过固定 SHA256 接受指定构建。不会修改、上传或提交原版文件。

## 构建处理

1. 校验三个原版 EXE 的哈希。
2. 按已验证的第二实例配置做等长产品名称和互斥对象名称替换，修改本机通信端口。
3. 校验中间文件哈希，避免字符串替换或修改位置出现偏差。
4. 在 PE 的 `.rdata` 已确认空白区域写入专用网卡 GUID，并更新该节的虚拟大小。
5. 修改界面两组及连接后台三组网卡查找/比较指令，从通用 `ComponentId` 过滤改为 `NetCfgInstanceID` GUID 匹配。原驱动类型检查仍保留。
6. 生成各实例自己的六字符产品身份、互斥对象前缀和端口。

源文件 `PatchEngine.cs` 记录原始文件哈希、指令位置及预期内容；这是一份指定构建的修改配置，不是通用 PE 自动分析器。要支持新构建，应重新分析并增加独立配置，不能只放宽哈希检查。

## 身份与目录

| 项目 | 原版 | 自动生成实例 N |
|---|---|---|
| 用户看到的目录 | `UniVPN` | `UniVPNN`，例如 `UniVPN3` |
| 内部产品身份 | `UniVPN` | `UVP003` 等六字符名称 |
| 服务 | `UniVPNService` | `UVP003Service` |
| 界面 / 连接后台 | `UniVPN.exe` / `UniVPNCS.exe` | `UVP003.exe` / `UVP003CS.exe` |
| 用户配置 | `%APPDATA%\UniVPN` | `%APPDATA%\UVP003` |
| 提权服务 RPC | 29190 | `29190 + N - 1` |
| 连接后台初始端口 | 19060 | `19060 + N - 1` |
| TAP | 原网卡 | 每次创建时新增，按 GUID 绑定 |

原程序内部依赖六字符产品名称推导安装路径。实际文件放在 `UniVPNN`，并通过原目录 `.univpn-multi\UVPxxx` 下的目录联接提供匹配的运行路径。启动服务、后台和界面均使用这个运行路径。

管理记录为 `instance-NNN.json`，包含身份、路径、端口、新网卡 GUID、创建状态和生成文件哈希。`Creating`、`Ready`、`Failed` 状态用于保留失败现场，不能把出现 `Ready` 理解为 VPN 已登录或业务连通。

## 并发与失败行为

- 使用独立的安装器全局互斥对象，避免两次创建同时分配编号。
- 编号综合已有目录、记录和服务，默认取最大值加一；识别早期的 `UniVP2` 实验实例。
- 创建前检查客户端和 TAP 状态，UAC 提权后与驱动调用前再次检查。
- 目标目录、服务名或指定端口被占用时停止，不覆盖已有实例。
- 打开已有实例会重新校验副本哈希、目录联接、服务路径和监听端口。
- 失败时保留部分结果，尽力停止属于本实例的服务，不删除原版、不卸载公共驱动。

## 当前限制

多实例不是独立 Windows 网络栈。路由、DNS 和终端策略仍可能互相影响；不同内网网段不重复有助于分流，但仍需要实际连接验证。未实现自动登录、凭据迁移、第三方认证适配、自动路由策略或完整卸载事务。

仓库的离线检查不启动 VPN。完整硬件/服务/认证链路需要在可恢复的实际环境中验证。
